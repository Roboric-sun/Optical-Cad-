# Поля и виньетирование — версия 0.8.1

Это первая часть этапа 0.8: табличный редактор угловых полей, четыре коэффициента виньетирования и расширенный импорт Geopter. В 0.8.1 добавлены высоты объекта и параксиального изображения. Дополнительные определения апертуры и расширенная асферика остаются следующими задачами [карты развития](ROADMAP_RU.md).

## Работа в интерфейсе

Откройте **Последовательный режим → Поля зрения**. Выберите определение поля; в строке задаются X/Y в градусах или миллиметрах, положительный вес и четыре коэффициента:

| Коэффициент | Сторона зрачка |
|---|---|
| VUX | +X |
| VLX | −X |
| VUY | +Y |
| VLY | −Y |

Значения задаются долями: 0 оставляет сторону целиком, 0.2 оставляет 80% её радиального размера, 0.4 — 60%. Допустимо `0 ≤ V < 1`; полностью вырожденная сторона и отрицательные коэффициенты в этой версии отклоняются. В таблице принимаются точка и запятая как десятичный разделитель.

Можно добавлять, удалять и перемещать строки. При перемещении ссылки решения по лучу и функции качества следуют за тем же полем. Удаление используемого поля требует сначала изменить соответствующую ссылку. Отмена диалога сохраняет проект; подтверждённые изменения поддерживают undo/redo. Если проект изменён, пока диалог был открыт, устаревшие данные отклоняются.

Общий диалог параметров системы сохраняет текстовые строки: `X Y вес` или `X Y вес VUX VLX VUY VLY`. Для перестановки полей со связями используйте табличный редактор.

## Три определения поля

| Тип в C++ / файле | Значение X/Y | Ограничения |
|---|---|---|
| `Angle` / 0 | Углы объекта, ° | Существующая конвенция: при конечном L объект имеет координаты −L tan(X/Y) на плоскости Z=−L |
| `ObjectHeight` / 1 | Координаты точки объекта, мм | Требуется L>0; лучи всех волн выходят из одной точки (X,Y,−L) |
| `ParaxialImageHeight` / 2 | Высота в гауссовом изображении, мм | Первичная волна, соосные преломляющие поверхности, конечное гауссово сопряжение |

Тип общий для таблицы, как в Geopter. При его смене числа X/Y **не конвертируются автоматически**: задайте координаты в новых единицах. Графики, легенда, селекторы анализа, редактор функции качества и CSV RMS показывают соответствующие единицы. Максимум: ±80° или ±1e8 мм; вычисленный эквивалентный угол также должен лежать в ±80°.

Для высоты изображения используется собственная матрица ABCD первичной волны в координатах (высота, n×угол). Объектная среда — AIR. На конечном расстоянии L коэффициент обратного увеличения `r=C×L+D`, и объектная точка равна `(r×X,r×Y,−L)`. При объекте на бесконечности входные наклоны равны `u_x=−C×X`, `u_y=−C×Y`. Реальная трассировка затем прицеливает каждую координату зрачка в STOP.

Это **параксиальная**, а не реальная высота пятна. Она относится к гауссову сопряжению, независимо от текущей плоскости приёмника. Дефокус и трассируемая длина волны сохраняют исходную точку/направление объекта. Изменение первичной волны или силовой геометрии пересчитывает перевод поля. В афокальных, наклонённых/децентрированных, зеркальных схемах и при `C×L+D=0` этот тип отклоняется.

Решение толщины по высоте реального луча поддерживает угол и высоту объекта. С параксиальным полем изображения оно отклоняется: это поле зависит от всей оптической силы, а решение использует изменяемую часть схемы. Дальнейшая поддержка потребует совместного решения этих зависимостей. Остальные геометрические pickup и локальная оптимизация используют текущую разрешённую геометрию.

Новые типы требуют **формата 6**, где `sequential.fieldType` обязателен. Неизвестные значения и попытка записать метаданные под форматами 1–5 отклоняются. Старые приложения отказываются открывать формат 6; угловые проекты продолжают сохраняться в подходящем старом формате. Примеры: `object_height.optcad` (L=200 мм) и `image_height.optcad` (объект на бесконечности).

Импорт Geopter поддерживает Field.Type 0/1/2 и коэффициенты. Определения сверены с [field_spec.h](https://github.com/heterophyllus/Geopter/blob/0edfbf52fcf0e3fc660e5ae33c354fd7a6be80d7/geopter/optical/include/spec/field_spec.h) и [OpticalSpec::update](https://github.com/heterophyllus/Geopter/blob/0edfbf52fcf0e3fc660e5ae33c354fd7a6be80d7/geopter/optical/src/spec/optical_spec.cpp). Это совместимость определений; численное сравнение с запущенным Geopter не выполнено. Для конечного углового поля наша прежняя конвенция отсчитывает угол от первой вершины, тогда как Geopter использует расстояние до входного зрачка: полная эквивалентность этого случая не заявляется.

## Что происходит с лучом

Пусть `u,v` — исходная нормированная координата в единичном диске зрачка. Перед прицеливанием в физический STOP применяется:

```text
u' = u × (1 − VLX), если u < 0; иначе u × (1 − VUX)
v' = v × (1 − VLY), если v < 0; иначе v × (1 − VUY)
```

Пример: EPD=10 мм, STOP на первой плоской поверхности, VUY=.4. Луч `v=1` теперь проходит STOP на Y=3 мм; при VUY=0 он проходил на Y=5 мм. Координата 0 остаётся 0 даже при разных коэффициентах сторон. Если перед STOP стоят оптические поверхности, учитываются увеличение зрачка и прицеливание по реальному лучу.

Световые апертуры поверхностей продолжают физически отсекать лучи. Коэффициенты задают используемый пучок для данного поля; их изменение может увеличить долю лучей, проходящих внутренние апертуры.

Решение толщины по высоте луча использует уже изменённое поле. При VUY=.4 выбранный верхний край означает `v'=.6`; толщина пересчитывается именно по этому лучу. Функция качества также получает расчёты текущего пучка.

## Анализы и единицы

Пятно, ray fan и OPD используют выборку исходного нормированного диска с последующим преобразованием координат. В CSV поля `pupil_x/pupil_y` и шкалы ray fan сохраняют исходные координаты. Спектральные веса и потери Френеля сохраняются; это существующая равномерная выборка пучка, без отдельного фотометрического интеграла якобиана преобразования. Доля успешных лучей оптимизатора относится к заданному пучку после преобразования.

FFT PSF/MTF рассчитывается на физической сетке зрачка. Для каждого физического узла выполняется обратное преобразование; узлы вне преобразованного диска остаются пустыми. Поэтому уменьшенный зрачок меняет ширину PSF и частотный срез MTF. Размер пикселя рассчитывается на общей исходной сетке, энергия PSF нормирована к 1.

Сохраняются ограничения текущей скалярной монохроматической модели Фраунгофера и приближения входного зрачка. Проверка сходимости для сложных схем, выходной зрачок и полихроматическая дифракция относятся к этапу 0.9. Нормировка PSF к 1 не измеряет абсолютную светопропускаемость объектива.

## Импорт и файлы

В Geopter JSON читаются VUX/VLX/VUY/VLY отдельно для каждого поля. Отсутствующая таблица означает нули; присутствующая должна иметь ровно столько числовых записей, сколько полей. Ошибочные массивы отклоняются. Формулы коэффициентов сверены с [полем Geopter в зафиксированном коммите](https://github.com/heterophyllus/Geopter/blob/0edfbf52fcf0e3fc660e5ae33c354fd7a6be80d7/geopter/optical/src/spec/field.cpp); реализация нашего преобразования собственная.

Файл [dbgauss.json](../examples/geopter/dbgauss.json) из того же коммита теперь импортируется через **Файл → Импорт Geopter JSON**. Он содержит 11 физических поверхностей, внутренний STOP, три поля и три волны. Коэффициенты Y второго поля .2/.25, третьего .4/.4 сохраняются. Световые апертуры отсутствуют в оригинале, поэтому импортёр оценивает их по фактическим пересечениям выборки лучей с небольшим запасом и ограничением областью поверхности. Это оценка для переноса, а не данные измеренных апертур исходного объектива.

Ненулевые коэффициенты требуют формата `.optcad` версии **5** и Optical CAD 0.8. Старые приложения отклоняют его. Без коэффициентов сохраняется подходящий прежний формат 1–4; прежние шесть собственных примеров остаются неизменными. Новый пример — `vignetted_singlet.optcad`.

Численная эквивалентность с запущенным Geopter/Zemax пока не заявляется. Проверки импорта, физических точек STOP и аналитической MTF описаны в [TESTING.md](TESTING.md).

## Для изучающего C++

```cpp
optics::Catalog catalog;
auto system = optics::SequentialSystem::demo();
system.fields[1].vuy = .2;
system.fields[1].vly = .25;
auto field = system.fields[1];
auto pupil = optics::vignettedPupil(field, 0, 1); // (0, .8, 0)
auto ray = optics::pupilRay(system, catalog, field,
                          system.wavelengths[system.primary].um, 0, 1);
auto path = optics::trace(system, catalog, ray);
```

`Field` хранит данные. В `src/core/field.cpp` находятся проверка коэффициентов и прямое/обратное преобразования. `pupilRay` применяет их до прицеливания; FFT использует обратное преобразование для физической сетки. `src/app/field_editor.cpp` отвечает за таблицу и сохранение идентичности полей; вычисления остаются в ядре.
